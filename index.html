What is autoformulation?

An optimization model has three parts. Decision variables are what we may choose. The objective scores a choice. Constraints say which choices are allowed. Once these are written precisely, solvers such as Gurobi or CPLEX find the best choice quickly.

Writing them down is the bottleneck. Real problems arrive as text, business rules and spreadsheets, and turning them into rigorous mathematics and executable code has traditionally been manual, slow and iterative work for experts.

Autoformulation hands that translation to a large language model, which reads the description and produces the model and the solver code.

Asking an LLM for the numerical answer directly does not work well, because feasibility and optimality cannot be guaranteed. Autoformulation separates language understanding from numerical optimization: the LLM builds the model, and a solver checks feasibility and optimality within its tolerances.

Why it is hard

i

Descriptions are incomplete

Bounds, units, index sets and default assumptions are often implicit. Words like "capacity", "shift" or "coverage" carry modeling meaning that ordinary language does not spell out.

ii

Modeling is a skill

Understanding the story is not enough. Choosing variables, separating hard constraints from soft preferences and applying standard patterns such as linearizations takes expertise.

iii

Running is not the same as right

Code can execute while solving the wrong problem. The real question is whether the generated model faithfully reflects the intended one.

When patching is not enough: refinement as search

Local repair fixes a missing constraint or a wrong API call. But if the modeling abstraction itself is poor, editing the same formulation goes nowhere. Refinement then becomes a search over candidate formulations in a symbolic space: a discrete set of expressions where distant-looking points, such as an edge-based and a position-based routing model, can be equivalent.

Numerical optimization moves along a gradient. Symbolic space has no derivatives, but solver evidence can be written in words. An infeasibility report, a failed behavioural test or a units check becomes a critique such as "trucks must be integers". That critique acts as a verbal gradient: it points toward a better neighbour.

Tree search over modeling thoughts, test-time search, and co-evolution of generators and verifiers are examples of this idea in the literature.

From the survey, Section 5

A two-level taxonomy of metrics

Systems produce different artifacts and fail in different ways: a formulation can be structurally wrong, code can fail to run, and an executable model can still return an infeasible or poor solution. The survey separates outcome-level metrics, which judge specific outputs, from system-level metrics, which judge the whole pipeline.

Recommended order of checks. Task success is defined on top of this pipeline by each benchmark's acceptance criterion, and should always be reported together with that criterion.
